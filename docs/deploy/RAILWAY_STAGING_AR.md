# تهيئة Railway آمنة قبل أي نشر إنتاجي

## الحالة
لا يوجد Deployment معتمد لهذا النظام حتى 2026-10-17. وجدنا عدة حسابات Railway متصلة، وكل الموجود تحتها مشاريع أخرى أو مشاريع غير مسماة لهذا النظام. لا تستخدم مشروعًا قائمًا عشوائيًا.

## الخطوات الصحيحة
1. اختيار مساحة العمل والمشروع المخصص لـ Social Publisher (وليس مشاريع Himma أو tlebotpost).
2. تقديم PostgreSQL 15+ منفصلة. لا تُشغل اختبارات TRUNCATE خارج قاعدة بيانات باسم *_test مع NODE_ENV=test.
3. إعداد `APP_ORIGIN` رابط HTTPS الصحيح، و`API_HOST=0.0.0.0` و`PORT` من Railway و`NODE_ENV=production`.
4. توفير `DATABASE_URL` بإعداد TLS والتحقق من الهوية بما يناسب مسار الاتصال الفعلي.
5. إدخال `LOGIN_THROTTLE_PEPPER` و`SECRETS_ENCRYPTION_KEY` من مدير أسرار الاستضافة. لا تُدخل مفتاح التشفير الرئيسي في داشبورد التطبيق.
6. تشغيل `npm run db:migrate` على قاعدة البيانات المقصودة قبل تشغيل API، ثم فحص `GET /health/ready` ليُعيد 200.
7. تشغيل `npm run admin:bootstrap` مرة واحدة فقط ببيانات الإدارة المؤقتة ثم حذف كلمة المرور الممرّرة من المتغيرات.
8. يجب أن يبقى `LIVE_PUBLISHING_ENABLED=false`؛ عامل النشر الحالي Offline فقط.
9. فحص تسجيل الدخول على HTTPS، Cookie Secure/HttpOnly، CSRF، الصلاحيات، التأخير، المراقبة، الصحة، ومسارات إعداد الحسابات مع بيانات وهمية فقط.
10. قبل النشر للعامة/البيانات الحقيقية: استكمال مراحل الأمان ومواءمة media وMeta وTelegram والتأكد من صلاحياتها.

## ملاحظات
- لا تُعطل فحوص التشفير/TLS للحصول على نشر أخضر.
- حدد مصدر GitHub والفرع بدقة؛ main بعد الدمج هو **كود التطوير** لا إصدار نشر إنتاجي.
- عندما يُطلب deployment، لا تتعامل مع URL مبني أو غير متحقق منه كرابط معاينة.
